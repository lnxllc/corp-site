計測・GA4

GA4の収益がECの売上と
合わない原因と確認手順

2026年11月20日 GA4eコマース計測

この記事でわかること

  • GA4の収益とECの売上を比べる前に、そろえておく4つの条件
  • GA4の収益が「少ない」とき・「多い」ときで分けたよくある原因6つ
  • 注文番号（transaction_id）でGA4と注文一覧を突き合わせる手順
  • 原因別の直し方と、完全に一致しない前提での判断の目安

結論：GA4の収益とECの売上は、もともと完全には一致しません。まず期間・税と送料・キャンセルや返品・通貨の4つの条件をそろえて比べてください。そのうえでGA4のほうが少ないなら、購入完了ページを通らない決済や同意バナーによる取りこぼし、transaction_idが空・固定で重複扱いされている可能性を疑います。GA4のほうが多いなら、完了ページの再読み込みなどによる二重計上を疑います。どれに当たるかは、注文番号ごとにGA4と注文一覧を突き合わせると短時間で分かります。広告の自動入札にGA4の収益を使っている場合は、差が広告の判断を狂わせるため、早めに直してください。

まず確かめる：比べる条件はそろっているか

「GA4の収益が売上と合わない」という相談の中には、計測の不具合ではなく、比べている数字の中身が違うだけのものがかなり含まれます。突き合わせる前に、次の4つをそろえてください。

条件ずれる理由そろえ方
期間とタイムゾーンGA4のプロパティのタイムゾーンと、ECの管理画面の集計基準（注文日・入金日・出荷日）が違うと、日の境目で売上が前後する1日単位ではなく1か月単位で比べる。ECの集計基準が「注文日」かを確かめる
税・送料・割引ECの「売上」に税・送料が含まれ、GA4に送っている金額には含まれていない（またはその逆）GA4に送っている value の中身を確かめ、EC側も同じ定義の金額で比べる
キャンセル・返品ECの管理画面ではキャンセル分が差し引かれるが、GA4には購入時点の金額が残るECの数字を「キャンセル前の注文金額」にそろえて比べる
通貨と対象チャネルEC側には電話注文・店頭受け取り・モール出店分などGA4の外の売上が含まれる自社サイト経由の注文だけに絞って比べる

なお、GA4の購入データは、送ってからレポートに出るまで時間がかかります。Googleの開発者向けの手順では、購入イベントのデータは約24時間後にレポートやデータ探索で確認できると説明されています。（出典：購入イベントを設定する｜Google for Developers）当日や前日の数字だけで判断しないでください。

ポイント：4つの条件をそろえても差が残ったら、そこからが計測の問題です。差が「GA4のほうが少ない」のか「多い」のかを先に決めると、疑う場所が半分に絞れます。

GA4の収益が売上と合わないよくある原因6つ

当社が計測の見直しで出会うことが多い原因は、次の6つです。GA4の収益が少なくなるものと、多くなるものがあります。

原因起きていることGA4の収益は
1. 購入完了ページを通らない外部の決済画面（後払い・キャリア決済・一部のカード決済など）から自社サイトに戻ってこない人の購入が記録されない少なくなる
2. 同意バナー・ブロックによる取りこぼしCookieの同意を得られなかった人、広告ブロックを使う人の購入イベントが送られない少なくなる
3. transaction_id が空・固定注文番号が入っていない、または全注文で同じ値になっていて、2件目以降が重複として除かれる少なくなる
4. value・currency の形式が違う金額が「¥1,000」のような文字列で送られている、通貨コードが入っていない欠ける・0になる
5. 完了ページの再読み込みで二重に送られる購入完了ページの再読み込み・ブックマーク・メールからの再訪で、購入イベントがもう一度送られる。注文番号が毎回変わる作りだと重複として除かれない多くなる
6. タグの二重設置ECカートの標準連携とGTMの両方から購入イベントを送っている多くなる

原因3と5は、どちらもtransaction_id（注文番号）が関係します。Googleのヘルプでは、同じトランザクションIDの購入イベントは重複として除かれること、IDが空の購入イベントはすべて重複として除かれること、注文ごとに一意の値（注文確認番号など）を使うべきことが説明されています。また、この重複の除外はウェブのデータストリームでのみ働き、アプリのストリームでは働かないとされています。（出典：[GA4] トランザクション ID を使用してキーイベントの重複を抑える｜アナリティクス ヘルプ）

原因4については、Googleのヘルプで、収益の指標を出すには購入イベントに value と currency などが必要であること、value は通貨記号を含まない数値で送ること、currency は「JPY」のような3文字のコードで送ることが案内されています。（出典：欠落した収益データを修正する｜アナリティクス ヘルプ）

「少ない」か「多い」かで原因を絞る

条件をそろえたうえでの差の向きと、ずれ方の形を見ると、原因の当たりがつきます。

GA4のほうが少ない

取りこぼし・重複扱いを疑う

  • 決済方法によって差が大きい → 原因1
  • 全体が一定の割合で少ない → 原因2
  • 件数が極端に少ない（数件しか出ない） → 原因3
  • 件数は合うのに金額だけ少ない・0 → 原因4か税・送料の定義

GA4のほうが多い

二重計上を疑う

  • 同じ注文番号が2回以上出てくる → 原因6
  • 注文番号が違うのに金額・時刻がほぼ同じ購入が並ぶ → 原因5
  • テスト注文や社内の注文が混ざっている
  • キャンセル分を差し引いていない（条件のずれ）

なお、GA4のレポートに「しきい値が設定されている」と表示されることがあります。Googleのヘルプでは、データのしきい値は年齢・性別などのユーザー属性や検索語句を含むレポートで、個人が特定されないよう一部の行を表示しない仕組みと説明されています。（出典：[GA4] データのしきい値について｜アナリティクス ヘルプ）売上の合計を比べるときは、ユーザー属性などで分けていない表で確かめてください。

注文番号で突き合わせる確認手順

原因を言い当てるいちばん確かな方法は、注文番号ごとにGA4とECの注文一覧を突き合わせることです。次の順で進めると、1〜2時間ほどで当たりがつきます。

確認の順番

  • 手順1：直近1か月の注文一覧をECの管理画面から書き出す（注文番号・注文日時・金額・決済方法・キャンセルの有無）
  • 手順2：GA4の「探索」で自由形式の表を作り、行に「トランザクション ID」、値に購入の件数と収益を置いて、同じ期間で書き出す
  • 手順3：表計算ソフトで2つを注文番号で照合し、「ECにあってGA4にない」「GA4にあってECにない」「両方にあるが金額が違う」の3つに分ける
  • 手順4：「GA4にない」注文を決済方法別に数え、特定の決済方法に偏っていないかを見る（原因1）
  • 手順5：「GA4にあってECにない」「同じ番号が複数」の行を見て、二重送信やテスト注文がないかを見る（原因5・6）
  • 手順6：テスト用の注文を1件入れ、GA4のDebugViewやGTMのプレビューで、購入イベントの transaction_id・value・currency の中身を確かめる（原因3・4）

手順2で「トランザクション ID」の行が「(not set)」ばかりになる場合は、注文番号がそもそも送られていません。GTMのプレビューがうまく動かないときは、GTMプレビューが接続できない原因と直し方も参考にしてください。

注意：書き出した注文一覧には、お客様の名前やメールアドレスなどの個人情報が含まれることがあります。突き合わせに使うのは注文番号・日時・金額・決済方法だけにして、不要な列は書き出さないか、作業後に削除してください。

原因別の直し方

原因1：完了ページを通らない

戻ってこない決済を把握する

  • 決済後に自社の完了ページへ戻る設定があるか、決済サービス側の設定を確かめる
  • 戻らない決済が残る場合は、その分はGA4に出ない前提で、ECの数字と分けて見る
  • サーバー側から購入を送る方法を検討する

原因2：同意・ブロック

差の割合を把握して扱う

  • 同意バナーの設定とGTMの同意設定が意図どおりかを確かめる
  • 取りこぼしはゼロにならないため、毎月の差の割合を記録する
  • 割合が急に変わったら、設定変更を疑う

原因3・5：transaction_id

注文番号をそのまま送る

  • ECの注文番号を、空にせず注文ごとに変わる値で送る
  • 完了ページを開くたびに番号を作り直す作りをやめる
  • 同じ注文で番号が変わらなければ、再読み込みは重複として除かれる

原因4・6：形式と二重設置

送り方を1本にそろえる

  • value は数値、currency は「JPY」で送る
  • カートの標準連携とGTMのどちらか一方だけで送る
  • 税・送料を value に含めるかを社内で決め、記録しておく

value に税や送料を含めるかどうかについて、Googleの設定例では、value は商品の金額の合計で、税（tax）と送料（shipping）は別のパラメータとして送る形になっています。（出典：購入イベントを設定する｜Google for Developers）どちらの定義にするかは会社ごとに決めてかまいませんが、ECの売上と比べるときに、どちらの定義の金額かが分かるようにしておくことが大切です。

直したあとは、テスト注文で正しく送られることを確かめ、1〜2週間後にもう一度注文番号で突き合わせてください。計測は、サイトの改修やカートの更新で再び止まることがあります。定期的な点検の仕組みは、GA4の計測が止まっていても気づけない？月1回の計測監査と異常検知の仕組みの作り方で整理しています。

どこまで合えばよいか：判断の目安

原因2のように、同意やブロックによる取りこぼしは、設定を正しくしてもゼロにはなりません。そのため当社では、完全な一致を目指すのではなく、次のように判断しています。

  • 差の割合が毎月ほぼ同じなら、傾向を見る用途には使える状態です。差の割合を記録し、施策の比較はGA4の中だけで行います
  • 差の割合が月によって大きく変わるなら、何かが止まったり二重に送られたりしています。直近のサイト改修・カートの更新・タグの変更を確かめてください
  • GA4のほうが多い状態は、取りこぼしでは説明がつかないため、必ず原因を直してください

差の割合の「許容範囲」には公式の基準はなく、決済方法の構成や同意バナーの有無で変わります。当社が実務で見ている目安では、条件をそろえたうえで1割前後の差に収まっていれば、傾向を見る用途には使えることが多いと考えています。

特に注意したいのは、GA4の収益を広告の成果としてGoogle広告などに取り込み、自動入札に使っている場合です。二重計上があると、広告が実際より成果を上げているように見え、入札が強くなりすぎます。広告の管理画面と社内の数字の差については、広告管理画面とCRMのCV数が合わない原因と対処法もあわせてご覧ください。

LnXの見解

GA4の収益が売上と合わないという相談では、計測の不具合そのものよりも、「何と何を比べているか」が社内でそろっていないことが出発点になっている場合が多いと感じています。税や送料、キャンセルの扱いをそろえるだけで、差の大半が説明できることも珍しくありません。

一方で、transaction_id の送り方の誤りや二重設置は、気づかないまま広告の自動入札に使われていることがあります。売上を目的にした広告で成果が読めないときは、広告の設定より先に、計測の土台を確かめる価値があります。

LnXの広告運用代行では、GA4やコンバージョン計測などの計測環境の構築・点検も含めて対応しています。「広告の成果と実際の売上が合わない」という段階からでもご相談ください。

※GA4の機能・画面・ヘルプの内容は更新されます。設定を変える前に、最新の公式情報もご確認ください。

よくある質問

QGA4の収益とECの売上は、完全に一致させられますか？

完全な一致は難しいと考えてください。Cookieの同意を得られなかった人や広告ブロックを使う人の購入は、GA4に送られないことがあるためです。条件をそろえたうえで、差の割合が毎月ほぼ同じかどうかで判断することをおすすめします。

QGA4のほうが売上より多いのはなぜですか？

購入完了ページの再読み込みや、カートの標準連携とGTMの両方から購入イベントを送っている二重設置が考えられます。同じ注文で注文番号（transaction_id）が変わらなければ、ウェブでは重複として除かれるため、注文番号の送り方から確かめてください。

QGA4の収益には税や送料を含めるべきですか？

どちらでもかまいませんが、社内で定義を決めて記録しておくことが大切です。Googleの設定例では、value は商品の金額の合計で、税と送料は別のパラメータとして送る形になっています。ECの売上と比べるときは、同じ定義の金額どうしで比べてください。

Qキャンセルや返品はGA4に反映されますか？

何もしなければ、購入時点の金額がGA4に残ります。ECの管理画面がキャンセルを差し引いた数字を出している場合は、比べるときにECの数字をキャンセル前の注文金額にそろえるか、返金のデータもGA4に送る設定を検討してください。

Qどのくらいの頻度で突き合わせればよいですか？

当社では、月に1回、注文番号での突き合わせか、少なくとも件数と金額の差の割合を確かめることをおすすめしています。サイトの改修やカートの更新をしたあとは、その都度テスト注文で確かめてください。
